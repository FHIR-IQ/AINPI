# 2026-08-16 update: a crosswalk from FHIR base URL to NPI, and the 83% it cannot cover

New download: [endpoint-org-crosswalk.csv](https://ainpi.dev/api/v1/findings/endpoint-org-crosswalk.csv).
It resolves 19,334 FHIR base URLs in the CMS National Provider Directory to the
organization that runs them, with the NPI attached. No login, no key.

That number is also the finding. The directory holds 114,071 FHIR REST
endpoints. Only 19,334 of them can be attributed to anyone.

## Why attribution is the whole problem

"There is a FHIR server at this URL" answers nothing on its own. The question
an integrator, a payer validating a network, or an auditor actually has is
whose server it is.

The NDH models that with `Endpoint.managingOrganization`. We measured how often
the link is there and resolves:

| | Endpoints | Resolve to an organization | Rate |
|---|---:|---:|---:|
| FHIR REST | 114,071 | 19,334 | 16.9% |
| Direct Trust | 1,246,514 | 110,984 | 8.9% |

The 94,737 unattributed FHIR endpoints are URLs with no owner in the directory.

Two things make that number more useful than it first looks.

**Nothing is broken, it is missing.** Zero references dangle. Every
`managingOrganization` that exists points at a real organization. We counted
presence and resolvability separately so we could not score a dangling
reference as a success, and the two came out identical. That distinction
matters: populating a field fixes absence, while breakage would need
referential-integrity repair. The first is a publishing change, the second is
an engineering project.

**Every endpoint that resolves reaches an organization with an NPI.** There were
no partial wins to discard. That is why the crosswalk works as a base URL to NPI
lookup covering 18,884 organizations.

## The gap is per-vendor, not systemic

Grouping by host changes the picture. Of the 30 hosts carrying at least 100
endpoints, 16 publish no organization link on any endpoint at all, covering
49,036 endpoints. Others attribute most of theirs.

| Host | Endpoints | Attributed |
|---|---:|---:|
| fhir4.healow.com | 6,617 | 68.4% |
| api.platform.athenahealth.com | 35,439 | 24.5% |
| fhir.fhirpoint.open.allscripts.com | 4,977 | 21.2% |
| fhir4.eclinicalworks.com | 16,809 | 0.0% |
| fhirpt.officeally.com | 13,090 | 0.0% |
| api.practicefusion.com | 4,714 | 0.0% |

A host at 0% has never populated the field, rather than populated it patchily.
That makes this addressable one vendor at a time instead of a single systemic
shortfall.

One warning for anyone tempted to shortcut this. Host is not a proxy for
organization. EHR vendors run thousands of tenants on one domain, so
`api.platform.athenahealth.com` identifies the vendor and never the practice.
Only the organization link separates them, which is exactly what is absent for
most endpoints.

## The directory does not yet carry payers

A separate question came out of the CMS provider-directory community. People
there describe the NDH as the eventual place to discover a payer's public
Provider Directory API, instead of hunting developer portals payer by payer.

We measured the distance between that idea and the shipped file. Of 114,071 FHIR
REST endpoints, 1 self-labels as a payer provider directory. No payer
organization type exists at all: `Organization.type` carries exactly three
codings across 1,999,818 typed resources, which are `prov`, `team` and `govt`.

We read the raw FHIR JSON rather than our own flattened column for this, so a
payer type could not have been hidden by our extractor.

The organization-identifier half is weaker than the endpoint half. Of the 92
payer-host endpoints the directory does carry, 7 have a managing organization.
The other 85 cannot be resolved to an entity.

A low count could simply mean payers have built nothing, which would not be the
directory's fault. So we added a control: Capital BlueCross serves a live,
public, unauthenticated FHIR provider directory, mandated under CMS-9115-F. It
is absent from the NDH entirely. That separates "nothing to index" from "not
indexed yet."

This is coverage of one release, not a compliance claim. Payer endpoints have
been discussed as direction. What we published is how far the current file sits
from it, which is the part anyone can act on.

## Phone, street address and coordinates are now queryable

The BigQuery tables behind the site gained flattened columns for telecom,
`address.line` and `Location.position`, so these no longer require scanning the
raw FHIR JSON.

Coverage on the 2026-05-08 release:

| Column | Practitioner (active) | Organization | Location |
|---|---:|---:|---:|
| Phone | 99.98% | 99.93% | 0.0% |
| Street address line | 85.7% | 66.5% | 98.4% |
| Latitude and longitude | | | 93.9% |

The practitioner column counts active practitioners, which is the same
denominator H43 used, so the two are comparable.

Two of those reproduce earlier findings without being asked to. Practitioner
phone at 99.98% matches [H43](https://ainpi.dev/findings/practitioner-phone-reachability)
exactly, and location phone at 0.0% matches its separate observation that
`Location.telecom` is empty in this release. Getting the same numbers by a
different route is the cheapest validation available.

Coordinates on 93.9% of locations are new capability. It is the only geography
in the NDH.

One implementation note worth passing on, because it fails silently. BigQuery
load jobs here run with `--ignore_unknown_values`, so a new field emitted by the
extractor is discarded without error unless the column already exists on the
table. Adding a field to the flattener alone looks like it worked and populates
nothing.

## Limits

The crosswalk covers the FHIR REST subset. Direct Trust addresses are messaging
addresses rather than callable base URLs, so they are reported at 8.9% linkage
and excluded from the download.

The payer provider-directory count is a floor. It counts servers that name
themselves in their URL path, so a directory at an unlabelled path would be
missed. The control probe exists because of that weakness, not despite it.
